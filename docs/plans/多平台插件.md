## 决策摘要

| # | 决策 | 采纳 | 可推翻条件 |
|---|---|---|---|
| 1 | 原生插件还是命令行配置 | 两个都做：各平台的原生插件包是主入口（钩子、MCP、密钥存储、更新都交给平台），`kioku` 命令只做插件做不到的事：停用自带记忆、迁移本地记忆、体检、浏览器授权 | 某个平台的插件机制不稳定到无法维护时，这个平台退回只用命令行写配置 |
| 2 | 安装源 | 本仓库同时当多个平台的源：Claude Code 与 Codex 的市场清单、根 `package.json` 的 `pi` 与 `dsh` 键、Hermes 装子目录；OpenClaw 与命令行发 npm | — |
| 3 | 提示词与格式放哪 | 照旧全在服务端，插件只转发；各运行时的差异用运行时家族区分 | — |
| 4 | 带会话上下文的场景（OpenClaw、Hermes 进群） | 第一版只做应用所有者本人的私聊与本机使用；群聊、他人私聊不注入、不上报、不接工具 | 服务端有了带会话上下文的工具接口之后再做 |
| 5 | 访问密钥 | 一个平台一个应用、一个访问密钥，不共用；优先用平台自己的密钥存储，没有的写权限 600 的文件 | — |
| 6 | 浏览器授权排在哪 | 排在 Codex、pi 之后、迁移之前：之前 `kioku setup` 先收手动粘贴的访问密钥，不挡前三个平台；之后的平台与迁移都用它 | — |
| 7 | 指令文件 | `AGENTS.md`、`CLAUDE.md` 是指令不是记忆，不迁移、不改 | — |

## 调研结论（2026-11-11）

三件事（会话开始注入、每轮召回、每轮结束上报）与带 Authorization 头的 HTTP MCP，六个平台都做得到。

| 平台 | 插件形态 | 安装 | 自带长期记忆 | 停用方式 |
|---|---|---|---|---|
| Claude Code | 外部命令钩子 | `.claude-plugin/marketplace.json` | auto memory | 用户设置 `autoMemoryEnabled: false`；插件自带的设置不生效，只能由命令行或用户改 |
| Codex | 外部命令钩子，输入输出与 Claude Code 接近 | `.agents/plugins/marketplace.json`（也读 Claude 的清单），`codex plugin marketplace add` | Memories，本地默认关 | 保持 `features.memories` 关闭 |
| pi | 进程内 TS 扩展 | `pi install git:…` 或 `npm:…`，无市场清单 | 没有 | — |
| Hermes | Python 的 `MemoryProvider`，同时只启用一个 | `hermes plugins install <仓库>/<子目录>` 或 pip | `MEMORY.md`、`USER.md` | `memory.provider` 选上之后，再关 `memory.memory_enabled`、`memory.user_profile_enabled` |
| OpenClaw | 进程内 TS，清单 `kind: "memory"` | ClawHub 或 npm | `memory-core` | `plugins.slots.memory` 设为本插件 |
| DeepSeek Harness | 进程内 TS（Cordis） | npm 或 `github:<仓库>` | 没有 | — |

动手前要实测的（调研里没能确认）：

- Codex：插件带的钩子在命令行下是否完整可用；钩子要用户在 `/hooks` 里信任一次。Stop 不带用户消息。注入超过约 2500 token 会落盘只留预览。
- OpenClaw：`before_prompt_build` 的返回字段；第三方记忆插件安装时会不会自动切槽位；换槽位后工作区的 `MEMORY.md`、`USER.md` 是否仍作为引导文件注入；拿对话内容要用户打开 `allowConversationAccess`。
- Hermes：MCP 配置的请求头是否展开环境变量；外部命令形态的钩子格式（用不上 provider 时的退路）。
- DeepSeek Harness：仍是开发者预览；是否兼容 Claude Code、Codex 的钩子（只有二手资料）；有没有压缩前的事件。
- pi：已迁到 `earendil-works/pi`，包名 `@earendil-works/pi-coding-agent`。

## 结构

要新增的目录（合并前在各自的 PR 里再说明一次）：

| 路径 | 内容 |
|---|---|
| `packages/core` | 各 JS 插件共用的实现：请求与报错、访问密钥格式检查、不跟跳转、从会话记录取最后一轮、打码、`kioku run`。从 `plugins/claude-code/lib` 挪出来 |
| `packages/cli` | `kioku` 命令，发 npm（`@kioku-memory/cli`）：`run`、`setup`、`doctor`、`login`、`import` |
| `plugins/codex`、`plugins/pi`、`plugins/hermes`、`plugins/openclaw`、`plugins/dsh` | 各平台的薄适配 |

约束：

- Claude Code、Codex 按插件目录复制安装，Hermes 只装子目录，装好之后引用不到目录之外的文件。所以共用核心要打进每个插件目录并提交，门禁重新生成并比对（做法照 `kioku_client` 的同步）。
- 插件里不放提示词与输出格式，失败时静默；`kioku` 命令是用户或 agent 主动执行的，失败时说明原因。
- 报错不带值与访问密钥的规则只在共用核心写一份。

`kioku` 命令的子命令：

| 子命令 | 作用 |
|---|---|
| `run` | 现有的凭据取用，不变 |
| `setup <平台>` | 停用或切换这个平台的自带记忆，写入访问密钥（平台没有密钥存储时）。改配置前显示差异、留备份，可以 `--dry-run`，`--undo` 还原 |
| `doctor` | 服务地址连不连得上、访问密钥的权限、钩子与 MCP 是否生效、自带记忆是否还开着 |
| `login` | 浏览器授权，拿到某个平台用的访问密钥（阶段 4） |
| `import --from <平台>` | 把本地记忆迁进 Kioku（阶段 5） |

## 浏览器授权的设计

照设备授权的流程做，命令行不用起本地端口，远程登录的机器上也能用。

1. `kioku login --platform <平台>` 向服务端申请：返回设备码（只给命令行）、短的确认码、确认页地址，10 分钟有效。
2. 命令行显示确认码并打开确认页。确认页在管理界面里，要求已登录。
3. 确认页显示：申请来自哪个平台、确认码（和终端里的逐字核对）、要建的应用（或选已有的同运行时的应用）、空间、权限范围的预览（用签发弹窗同一套表格）。默认模板不含凭据能力与机密级，要的话在这一页改。
4. 确认后服务端建应用、签发访问密钥；命令行轮询，凭设备码取走一次明文，之后这条申请作废。
5. 命令行把访问密钥交给平台的密钥存储，或写权限 600 的文件。

要守住的：

- 设备码与确认码只存哈希，一次有效，过期与用过的由定时清理删；申请与轮询限流。
- 确认页写明「只在终端里显示着同一个确认码时确认」：防别人发来一个链接骗取访问密钥。
- 签发照常按确认人的角色收紧（`clampScopesToRole`），非空间所有者不给凭据能力。
- 明文只在取走那一次的响应里，不进日志、不进变更记录。

## 需要你手动做的事

### U01　建 npm 组织

- **在哪**：npmjs.com，你的 npm 账号（没有就先注册，开两步验证）。
- **操作**：头像 › Add Organization，名字填 `kioku`，选免费的公开计划。名字被占用时换一个（例如 `kioku-memory`）。
- **验证**：`npm org ls <组织名>` 列出你自己。
- **回滚**：组织设置里删除。
- **告诉 agent**：「npm 组织建好了，scope 是 @xxx」。

说明：不带 scope 的 `kioku` 已被别人的包占用。`@kioku` 这个 scope 是否空着从外面查不出来，以建组织时的结果为准。

### U02　给每个包配受信发布

- **在哪**：npmjs.com，每个包的 Settings › Trusted Publisher。
- **操作**：选 GitHub Actions，填本仓库的所有者与仓库名、workflow 文件名 `release.yml`。包要先存在才能配：第一次由你在本机发一个占位版本（`npm publish --access public`，agent 会备好目录），配好之后的版本都由 CI 发。要配的包：命令行、OpenClaw 插件，后面如有 DeepSeek Harness、pi 的 npm 包再加。
- **验证**：包的设置页显示已配置的受信发布者。
- **回滚**：在同一页删除。
- **告诉 agent**：「受信发布配好了」。

说明：受信发布用 GitHub 的 OIDC 换一次性的凭证，仓库里不放 npm 令牌，发出的包自带来源证明。

### U03　审阅并合并 release.yml

- **在哪**：本仓库的 PR。
- **操作**：agent 开 PR 加 `.github/workflows/release.yml`（推版本 tag 时发 npm，只声明 `id-token: write` 与 `contents: read`）和 CONTRIBUTING.md 的「发布」一节。workflow 属于禁区，由你审阅后合并。
- **验证**：合并后在 Actions 里看得到这个 workflow。
- **告诉 agent**：「release.yml 合了」。

### U04　发起第一次发版

- **在哪**：对话里。
- **操作**：说「发 vX.Y.Z」。agent 改号、开发布 PR、推 tag，CI 发包。
- **验证**：`npm view <包名> version` 是新版本，包页面有 Provenance 标记。
- **回滚**：`npm deprecate` 标记弃用；72 小时内可以 `npm unpublish`。

### U05　OpenClaw 上架 ClawHub（可选，阶段 7）

- **操作**：注册 ClawHub，`clawhub package publish`。不上架时用户用 `openclaw plugins install npm:<包名>` 也能装。
